= CLI
:description: Every scoutjobs command. Skills use these; so can you.

[source,console]
----
$ scoutjobs help
----

Add `--json` to any read command. `SCOUTJOBS_HOME` overrides the data directory. `--compact` on `brief` and `job list` drops long text.

== Setup

[cols="2,3"]
|===
| Command | Does

| `scoutjobs init` | creates `~/.scoutjobs`: `config.yaml`, `profile.md`, `preferences.md`, `cv/`, `scoutjobs.db`
| `scoutjobs path` | prints the data directory
| `scoutjobs version` | prints the version (`dev` for a local build, the tag for a release)
| `scoutjobs serve [--addr 127.0.0.1:7070]` | dashboard and JSON API
| `scoutjobs mcp` | MCP server on stdio, every command as a tool; see xref:mcp.adoc[]
| `scoutjobs doctor` | install health: PATH, data dir, unknown config keys, mail password in the environment, skills linked per agent, Codex prompts, dashboard up; `--online` adds one GET to GitHub and says whether a newer release exists; `--json` for agents
| `scoutjobs update` | installs the latest release over this binary after a checksum check; `--check` only reports, `--yes` skips the question, `--version vX.Y.Z` picks a tag. Homebrew and distro-package installs are handed to their package manager. See xref:install.adoc#_updating[Updating]
| `scoutjobs export` | full JSON dump, for backup
|===

== Jobs

[source,console]
----
$ scoutjobs search --query "senior go engineer" --remote --add        # remote boards, add as new
$ scoutjobs search --board greenhouse:stripe --board lever:netlify     # ATS boards: greenhouse, lever, ashby, workable, smartrecruiters, personio, recruitee, bamboohr
$ scoutjobs search --board https://jobs.ashbyhq.com/linear --query go   # a careers URL works as a board too
$ scoutjobs search --rss https://example.com/jobs.rss --query go         # any RSS or Atom job feed
$ scoutjobs search --query "go engineer" --remote --location Berlin --hide-mismatches   # in or open to Berlin, nothing that breaks a must
$ scoutjobs search --suggest                                            # searches built from profile.md
$ scoutjobs job add --from https://boards.greenhouse.io/stripe/jobs/123  # one posting by URL: fields and description filled from the ATS
$ scoutjobs job add --company Stripe --title "Backend Engineer" --url https://... --remote hybrid --tags go,postgres
$ scoutjobs job import jobs.json          # bulk add from any JSON list
$ scoutjobs job list --open               # or --status applied, --q stripe, --json, --compact
$ scoutjobs job show 3 --json             # job, dir, events, interviews
$ scoutjobs job set 3 --status applied --note "via Greenhouse"
$ scoutjobs job set 3 --score 78 --fit-notes "Go+Postgres strong; no k8s"
$ scoutjobs job set 3 --contact hr@stripe.com
$ scoutjobs job set 3 --veto "work permit: no sponsorship"   # hard failure outside the score; --veto '' clears it
$ scoutjobs job fit 3 --file review.json   # evidence-backed review: writes fit-review.json, sets score, notes, veto
$ scoutjobs job review 3 --verdict send|fix --notes "..."   # the draft-reviewer's verdict, read by the grounding gate
$ scoutjobs job check 3 [--json]          # quality gates; exits 1 while a gate fails
$ scoutjobs job acknowledge 3 --notes "adjacent experience" --yes   # apply on a portal with must-have gaps
$ scoutjobs job check 3 --allow-acknowledged   # acknowledged gaps count as decided
$ scoutjobs job run 3                     # prepare the whole application with your agent CLI; nothing is sent
$ scoutjobs job run 3 --steps tailor,cover --agent codex [--force] [--keep-going] [--dry-run]
$ scoutjobs job skip 4 --reason "onsite only" --signals '{"remote":"onsite"}'
$ scoutjobs job rm 4
----

`search` matches every word of a query as a whole word, accepts several `--query` and `--board` flags, deduplicates by company plus title, and upserts on `--add` (an `=` after the id means already tracked). `--limit` and `--json --compact` keep the output small.

Every posting gets derived fields from its title, the board's tags and the description: `skills`, `level` (intern to principal, or manager), `employment` (full-time, part-time, contract, freelance, internship), `regions` (the countries and regions it is in or open to, or `worldwide`) and `visa` (`yes` or `no` when the posting says). They are added to the job's tags on `--add` as plain skills plus `level:`, `type:`, `region:` and `visa:` tags.

With a filled `profile.md`, results are ranked by a match score (FIT, 0 to 100): target role 20, skills 45, level 15, work mode 10, place 10, minus what the preferences avoid (`stack_avoid`, `on_call`). A `!` marks a posting that breaks a must: the wrong place, an engagement listed under deal-breakers, or a top of range below the salary floor; `--hide-mismatches` drops those. `--json` carries the score with the reasons in `match`. `--rank=false` keeps the board order.

`--location` takes cities, countries or regions (`Berlin`, `Germany`, `Europe`, `EMEA`, `LatAm`). An on-site or hybrid job matches when it is in the city, or in the country or region you named; a remote job matches when it is open to your country or region, or worldwide. A posting that states no place stays in.

A board is `source:slug` or the careers URL you would paste from the browser: `boards.greenhouse.io/<slug>`, `jobs.lever.co/<slug>`, `jobs.ashbyhq.com/<slug>`, `apply.workable.com/<slug>`, `jobs.smartrecruiters.com/<company>`, `<slug>.jobs.personio.de`, `<slug>.recruitee.com`, `<slug>.bamboohr.com`, or any feed URL ending in `.rss`, `.xml`, `.atom` or `/feed`. `--remote` adds Remotive, RemoteOK, Arbeitnow, Jobicy, Himalayas and the current Hacker News "Who is hiring" thread. LinkedIn, Indeed, Glassdoor, XING and StepStone have no public API and forbid scraping: the error says so, and the posting text goes into `job add --notes` by hand.

`job fit` takes the review JSON the `fit-review` skill produces: one row per material requirement with the posting's wording, `kind` (`must` or `nice`), `evidence`, `strength` (`direct`, `adjacent`, `partial`, `gap`), `confidence`, the defensible `wording` and the `risk`; `vetoes` with `rule` and `reason`; `score` and `notes`. Unknown values are refused. The file lands as `fit-review.json` in the application folder and the job's score, notes and veto follow it.

`job check` runs eight gates and prints `PASS`, `WARN`, `FAIL` or `SKIP` per line: `documents` (tailored resume and cover letter present and not stubs), `format` (warns when resume.md has other sections, or another order, than the main CV `cv/resume.md`), `fit_review` (no veto on the job or in the review), `coverage` (no must-have `gap`, every must-have `wording` appears in the drafts), `grounding` (a `review:send` event newer than the last edit of the drafts), `duplicates` (no paragraph twice, cover letter not identical to another application's), `ats_text` (`resume.pdf` has fonts and a text layer, is not encrypted, under 5 MB), `filenames` (ASCII, known types; warns on spaces, `final`, `(1)`). `email send --yes` runs the same gates and refuses on a failure; `--skip-checks` sends anyway and logs `check:skipped` with the list on the job. Gates block sending only: `cv export <id>` always writes the PDF and prints what still blocks sending (`--skip-checks` is accepted there for older scripts).

`job acknowledge` is for applying on an employer portal although the fit review lists must-haves without evidence. It prints every gap and, with `--yes`, records `check:acknowledged coverage: <gaps> | <notes>` on the job and moves a new or ranked job to `drafted`. Only coverage gaps can be acknowledged: a veto, missing documents, an unreviewed draft or a missing PDF still have to pass. Nothing changes in `fit-review.json`, a gap stays a gap, and the drafts must still not claim it. `job check --allow-acknowledged` then shows the gate as `ACK`; a new or changed gap needs a new acknowledgement. `email send` ignores acknowledgements. Apply on the posting yourself, then `job set <id> --status applied`.

`job run` prepares one application end to end, in dependency order: `fit` (fit review), `tailor` (resume.md), `cover` (cover-letter.md), `review` (draft review verdict), `export` (resume.pdf), `ats` (CV check against the job), `check` (every quality gate) and `draft` (email.json). An installed agent CLI does the AI steps with the same skill texts as the plugin, which are built into the binary: Claude Code (`claude -p`, restricted to reading the data folder and writing the application folder), Codex (`codex exec` in a workspace-write sandbox) or any command set as `agent_command` in config.yaml that reads the prompt on stdin. Pick one with `--agent` or `agent:` in config.yaml; otherwise the first one found is used. The agent reaches your data only through the `scoutjobs mcp` server, which refuses Gmail, sending and nested runs during a job run. ScoutJobs does the other steps itself. A step whose output already exists is skipped (`--force` redoes it), so running again resumes after a failure. Before planning, files an older version or an agent left in a differently spelled folder (`acme-go-engineer` for `acme_go-engineer`) are merged into the job folder; a file that differs from the one already there is kept in both places and reported as `files:conflict`, never overwritten. The agent writes its draft review to `review-result.json` and its ATS score to `ats-result.json` in the application folder, and ScoutJobs records them itself. Failed quality gates never stop the run: `export` and `check` finish as `warn` with the blockers, and the e-mail draft is still made. A draft review that asks for fixes stops the run with its notes unless `--keep-going` is passed, which records it as a warning. Any other failure stops the run with its reason, and every step is logged as a `run:<step>` event in the job's Activity. Each result is bound to the bytes it covered, in `provenance.json` in the application folder (SHA-256 per file): the draft review to the final documents (`resume.md`, `cover-letter.md`, and any resume or cover letter PDF or DOCX you put there yourself), each `resume.pdf` export to its `resume.md`, and the ATS score to the file scored. When one of those files changes, the step is stale and runs again: replacing the exported `resume.pdf` with your own final CV reopens the draft review and the ATS check, and the grounding gate blocks sending until the new file is reviewed. A run never overwrites a `resume.pdf` you put there; only `--force` on `export` does. Ctrl-C cancels; a run stops after 30 minutes. Nothing is sent: the last step is a local draft you review before `email send`. The dashboard's job page does the same with Prepare application, and the API with `POST /api/jobs/{id}/run`.

`job add --from <url>` fetches one posting from the same ATSes (Greenhouse, Lever, Ashby, Workable, SmartRecruiters, Personio, Recruitee, BambooHR) and fills every field you did not pass; the description lands in `notes` so the fit score has text to read. Flags you pass win over the fetched values.

== CV and e-mail

[source,console]
----
$ scoutjobs cv files                      # what is in ~/.scoutjobs/cv
$ scoutjobs cv export [3] [--file resume.md] [--skip-checks]   # resume.md to resume.pdf: job folder with an id, else ~/.scoutjobs/cv
$ scoutjobs cv cover 3 [--template cv/letter.docx] [--json]    # cover-letter.slots.json into the Word template
$ scoutjobs cv log --file resume.pdf --score 72 --ats 64 --summary "..." --gaps "a,b,c" [--job 3]
$ scoutjobs cv list [--limit 20]
$ scoutjobs email draft 3 [--to hr@...] [--subject "..."] [--body file.md] [--attach x.pdf]
$ scoutjobs email show 3 [--json]         # the draft, and a mailto: link
$ scoutjobs email send 3 --yes [--skip-checks]   # refuses without --yes, and while a quality gate fails
$ scoutjobs email test [--to addr]        # probe: sends one line to yourself, checks IMAP login when imap_host is set
$ scoutjobs email sync [--since 14d] [--via gmail|imap] [--dry-run] [--json]   # log replies to applications; never reads mail older than your first tracked job; --json adds "review": unmatched mail that may concern the search
$ scoutjobs gmail setup [--file client_secret_….json] [--no-connect]   # links the Google Cloud steps, imports the client JSON from ~/Downloads, connects
$ scoutjobs gmail connect | status | disconnect
$ scoutjobs gmail test                     # reads a few inbox headers and the next 14 days of your calendar; reports each
$ scoutjobs gmail draft 3                 # the application e-mail as a Gmail draft; you send it from Gmail
----

`cv cover` builds the cover letter from a Word template (`cover_template` in config.yaml, or `--template`) and the slot values in `cover-letter.slots.json`. Each `{{slot}}` is replaced in the run where it starts, so it keeps that run's font and emphasis even when Word split the placeholder; a paragraph that held only slots left empty is removed; every other part of the file (styles, fonts, page setup, headers and footers, numbering, images) is copied byte for byte. It writes `cover-letter.docx`, `cover-letter.md` with the same words for the review and the e-mail body, and, when LibreOffice is installed (`soffice` on `PATH`, the macOS app, or `SCOUTJOBS_SOFFICE`), `cover-letter.pdf`. It then checks: required slots (`employer_name`, `salutation`, `body_paragraph_1`, `signoff`, `candidate_name`) filled and every slot within its length, no slot the template lacks, `employer_name` naming the job's company, a recipient name or postal address only when `posting.md` or the job states it, no placeholder left, the same paragraph and run formatting and page setup as the template, no more pages than the template renders to and, with `pdftotext`, the PDF's text layer holding the DOCX wording. The result is `pass`, `warn` (not rendered, so the page count is unknown) or `fail` with the problems, and is recorded in `provenance.json`. During `job run` with a Word template the `cover` step writes only the slots and ScoutJobs builds the letter; the `cover_template` gate blocks sending while the check fails or when the slots, the letter or the template changed after the build.

`gmail setup` stores the Desktop OAuth client in `gmail-client.json` (0600) in the data dir and the token in `gmail-token.json`. The dashboard's Inbox page does the same with Connect Google when it is opened on `127.0.0.1` or `localhost`: it links each Google Cloud step, watches `~/Downloads` for the `client_secret_….json` download and offers to import it. Gmail and Google Calendar share this one Desktop OAuth client and one sign-in; there is no separate Calendar setup. Your events show on the dashboard Calendar page, and `calendar sync` (or the dashboard, every few minutes) keeps interviews in step both ways, writing only events ScoutJobs created. A Desktop client needs no registered redirect URI: Google accepts any loopback address, so open the dashboard on `127.0.0.1` or `localhost`. The client ID and secret come from the imported `gmail-client.json`, or from `gmail_client_id` and `gmail_client_secret` in config.yaml (`$SCOUTJOBS_GMAIL_CLIENT_SECRET` overrides the secret); a config.yaml ID without a secret uses the secret of the imported client with the same ID. Edits apply on the next Connect, without a restart. When the ID or the secret is missing, Connect stops before Google's consent page and names what is missing, never the value; a sign-in started from the Calendar page reports there. Tick every box on Google's consent screen: Connect and `gmail status` name any permission left out. Publish the app (Google Cloud > Audience > Publish app): while it is in Testing, Google ends the connection after 7 days, which `gmail status` and the Inbox page warn about before it happens and report after.

== Decisions, preferences, learning

[source,console]
----
$ scoutjobs decision log --job 4 --kind skip --reason "..." --signals '{...}'
$ scoutjobs decision summary              # what learn-preferences reads
$ scoutjobs pref set remote "remote or hybrid" --source stated [--confidence 1]
$ scoutjobs pref list | rm <key> | render  # render rewrites preferences.md
$ scoutjobs interview add 3 --stage technical --at 2026-10-20T14:00 --duration 45 --location https://meet.example/abc
$ scoutjobs interview list | set <id> --outcome passed     # set also takes --at, --duration, --location
$ scoutjobs linkedin import ~/Downloads/Basic_LinkedInDataExport.zip   # profile to linkedin/profile.md, connections for referrals
$ scoutjobs contacts 3                    # who you know at the job's company; --company Acme, --json
$ scoutjobs session log --kind mock_sysdesign --topic "rate limiter" --score 70
$ scoutjobs session list
$ scoutjobs learn add --skill Kubernetes --priority 1
$ scoutjobs learn list | set <id> --status in_progress --hours 2
----

== Reports

[source,console]
----
$ scoutjobs stats                         # funnel, weekly numbers, follow-ups due, stale
$ scoutjobs brief [--compact]             # everything the daily briefing needs, as JSON
----

`brief` returns `stats`, `upcoming_interviews`, `new_jobs`, `ranked_jobs`, `drafted_jobs`, `learning`, `preferences`, `recent_activity` and `config` in one call.
