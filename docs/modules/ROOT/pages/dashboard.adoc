= Dashboard
:description: What each page of the localhost dashboard shows and what you can do on it.

[source,console]
----
$ scoutjobs serve                     # http://127.0.0.1:7070
$ scoutjobs serve --addr 127.0.0.1:8080
----

One Go binary, SQLite, HTML templates, one small embedded script, no external assets, strict Content-Security-Policy. Light theme by default, `theme: dark` or `theme: auto` in `config.yaml`, and a switch in the sidebar that overrides per browser. The pages have no login, so keep it on localhost (see xref:security.adoc[]).

For a step-by-step tour from an empty install to an interview in your calendar, see xref:getting-started.adoc[].

image::overview.png[The overview: next best move, the four numbers, pipeline health, today's tasks, interviews, CV health, learning and recent activity,1200]

== How it works

The dashboard is a second window onto the same `~/.scoutjobs` the CLI and the agents use. It reads the SQLite database and the application folders on every request and renders plain HTML, so what you see is always the current state: no cache, no sync, no account. Every button on a page posts the same form a CLI command would run, and every change lands in the `events` table, which is what the *Activity* page and the agents' `scoutjobs job show` read back. Nothing is stored in the browser except the theme cookie.

The agents never open the dashboard. They write through the CLI (or the JSON API from a cloud runner), and you watch the result here: a new card after `job add`, a score gauge after the `job-fit` skill runs, the tailored resume in the drafts viewer after `resume-tailor`, the gates turning green after `draft-review` logs its verdict. The one place the loop closes the other way is the drafts viewer: an edit you save there is the text the agent reads on its next turn.

Because every page is a plain `GET` and every action a `POST` with a redirect, the whole thing works with the keyboard and in a reader mode. The one script (`app.js`, served from the binary under the same Content-Security-Policy) only adds to that: drag and drop on the board on top of the stage buttons, the progress bar and elapsed time while the AI assistant runs, the search tag filter, the connection tests, and a reload offer when the binary was upgraded. It talks to nothing but the dashboard's own forms and JSON.

== Overview

The page opens with *Next best move*: one card the server picks from the state of the pipeline, in this order: the strongest draft waiting to be sent, a follow-up past its date, an interview to prepare, a CV that has never been checked, otherwise new jobs to find and score. The four numbers next to it are open jobs, applications this week against `weekly_apply_target`, upcoming interviews and the response rate over everything applied. *Pipeline health* is the funnel, *Applications per week* the last eight weeks as bars labelled by the Monday that starts each week (the last one is *now*; hover a bar for its count), and *Today* the tasks due now with a button each. An interview whose time has passed without an outcome tops *Today* as "How did the Stripe system design interview go?" with *Log outcome*, so the pipeline moves on. Two rows come from the automation (see <<_automation>>): *N new jobs from your daily searches* links to the pipeline sorted by fit, and *Review follow-up to Globex* opens a follow-up e-mail ScoutJobs already drafted for a quiet application, so you only read and send it. The bottom row shows upcoming interviews and drafts waiting, CV health, the top learning gaps and the latest activity, written in plain words (*Status changed*, *Job added*) rather than event codes.

Dates read the way you would say them: *today 10:00*, *yesterday 16:00*, *13 Oct* within this year and *2 Mar 2025* before it. The same wording is used on the overview, the inbox day headings, the job page and the file lists.

== Navigation

image::sidebar-folded.png[The sidebar folded to icons, with the Pipeline tooltip showing,1200]

The sidebar groups the pages by what you are doing: *Apply* (Find jobs, Pipeline, Inbox), *Interview* (Interviews, Calendar, Learning) and *You* (Profile & CV, Connections, Preferences, Reviews, Activity). The button next to the logo folds it to a rail of icons and back; the choice is kept in a cookie. Folded, each icon shows its name in a tooltip on hover or keyboard focus, and the badges (upcoming interviews) stay visible. Tooltips across the dashboard are the same accessible kind: they appear on focus as well as hover, are read out by screen readers, and close with `Esc`.

=== Command palette and shortcuts

image::palette.png[The command palette: typing st lists the Stories page, the Stripe job and the matching actions,1200]

Press `Ctrl K` (`⌘K` on a Mac), or *Jump to…* at the top of the sidebar, to search every page, every job by company, title, `SJ-` number or stage, and a few actions: *Add job*, *Sync mail* and *Run daily searches and drafts now*. Type a few letters in any order of the words, move with the arrow keys, `Enter` opens, `Esc` closes and puts the focus back where it was. The jobs come from `/palette.json`, the same page-level data the pipeline shows.

Without the palette, `g` then a letter jumps to a page: `g o` overview, `g p` pipeline, `g i` inbox, `g c` calendar, `g s` find jobs. On the pipeline `/` focuses the search box and `f` toggles full screen. `?` lists every shortcut. None of them fire while you type in a field.

== Pipeline

image::pipeline.png[The pipeline board: one column per open stage, a fit ring per card,1200]

One column per stage, left to right in the order a job moves. Each card carries the fit gauge (green from 75, amber from 50, red below), where and how remote the job is, the deadline or last update, the source board, and the buttons for the stages that usually come next. A job with a veto shows the `veto` badge instead of a gauge, so a hard failure never hides behind a good number.

Drag a card onto another column to move it; the closing stages that have no column yet (hired, rejected, no response, withdrawn, offer declined, skipped) appear as drop targets under the board while you drag, so they do not take space the rest of the time. The *Due this week* toggle keeps only jobs with a deadline inside seven days or a follow-up due, and the search box filters on company, title and tags as you type. *Add job* opens the same form as `scoutjobs job add`, with *Fill from a posting URL* for the boards the search knows.

In the *List* view each new or ranked job without a veto has a checkbox. Tick a few and press *Prepare selected with AI*: they join the AI assistant's queue and run one after another through the same steps as *Continue with AI*. A strip on top of the pipeline says what is running and how many wait, and updates by itself. The dark theme uses the same layout with its own contrast-checked tokens:

== Job

image::job.png[One job: let AI finish this application, the step checklist, the drafts and the job details,1200]

The job page is where an application gets made. The stage line under the title shows how far the job has come. *Let AI finish this application* has one button, *Continue with AI*: the AI assistant chosen on Connections checks the fit, tailors the resume, writes the cover letter, reviews both against `profile.md`, renders the resume PDF, runs the hiring software check and prepares the application e-mail. *Options* picks which steps to run. While it runs, a progress bar shows the step it is on and how long it has been going; the page reloads when it ends.

The checklist on the right shows each step: green when done, amber when it needs a look, red when it blocks, with *Preview*, *Edit drafts* or *Details* next to it. A result is marked *stale* when a file it covered changed since, and the next run offers that step again. Opening the page records the agent results a stopped run left behind, so the last run's steps show as *now recovered* or *now stale*. With a Word cover letter template, the Documents panel lists `cover-letter.docx` and `cover-letter.pdf` with the template check; the Cover letter step is done only when that check passes.

*Drafts* holds the resume, the cover letter and the e-mail, each with *Preview* and *Edit*; *Mail app* opens your own mail program with the e-mail filled in. The right column holds the facts the agents also read (company, role, place, salary, source, skills) and *Application*, with buttons for the stages that usually come next. *Emails*, *Interviews*, *Files* and *Activity* tabs show everything else about the job.

image::keywords.png[Keywords to add: one requirement the tailored CV does not word yet, with the backing line from profile.md and Fix with AI,760]

*Keywords to add* lists the requirements the tailored resume does not say in the posting's words yet: the agreed wording from `fit-review.json` that is missing from `resume.md`, and the gaps of the latest CV check for this job. Each row shows where it came from and the line in `profile.md` that backs it. *Fix with AI* reruns the tailor and review steps with only the backed wordings added; a gap with no evidence in your profile is listed but never written into the CV.

image::job-gates.png[Ready to send: one check still to fix, and why the job fits with evidence from profile.md,760]

*Ready to send?* runs the same seven quality gates as `scoutjobs job check` on every page load: the documents exist and are not stubs, the fit review has no veto, every must-have is covered and its agreed wording is in the drafts, the draft-reviewer logged a `send` verdict after the last edit, nothing is duplicated, `resume.pdf` has a text layer, and the filenames look professional. A warning never blocks; a failure does, and the panel says what to do about each one:

image::job-blocked.png[A drafted job: the review asked for fixes and the resume PDF is not made yet,1200]

*Apply with gaps* appears when must-haves have no evidence. Tick each gap, say why you apply anyway, and press *Proceed with gaps*: the decision is logged as `check:acknowledged`, the fit review is not touched, and e-mail sending stays blocked. Once every other gate passes, *Proceed to official application* opens the posting, and *Yes, mark applied* records the submission with an optional note. Nothing is submitted for you.

*Why this job fits* is `fit-review.json`, one row per requirement: the posting's wording for each requirement, whether it is a must or a nice-to-have, where in your profile the evidence is, how strong the match is (direct, adjacent, partial, gap), the wording the CV may use, and the risk a reviewer could raise. Below it the free-text notes, then interviews and the full history of the job. *People you know here* lists your LinkedIn connections at the company after `scoutjobs linkedin import`, for asking a referral.

== Drafts viewer

image::drafts.png[The drafts viewer: cover-letter.md rendered, with Edit and Download,1200]

`/jobs/\{id}/files/\{name}` renders a text file from the job's application folder: the posting, the tailored resume, the cover letter, the e-mail draft, research, the prep sheet. *Edit* opens drafts (`.md`, `.txt`, `.json`) in a textarea: edit, save, and the agent sees the new text on its next read; the save logs `draft:edited` and the grounding gate asks for a fresh review. `.eml` files are read-only. Binary files (PDF, DOCX) are listed but not rendered.

== Search

image::search.png[Find jobs: what kind of job, where, remote only, posted, salary and the suggestions from your profile,1200]

The same sources as `scoutjobs search`, prefilled from `search_queries`, `search_boards` and `search_remote` in `config.yaml`. Paste a careers page URL or a `source:slug` into *Boards*; results list company, title, place, source and date with *+ Add to pipeline* each, or *Add all to pipeline* tracks every hit as `new`. A posting already in the pipeline shows its stage instead of the button. Postings are stored as text and never followed.

image::search-results.png[Search results: a score and label per job, what fits and what does not,1200]

With a filled `profile.md` the results come best fit first, each with its match score, a label (*Great match*, *Good match*, *Weak match*, *Breaks a must-have*), what fits (target role, skills, level, place) and what does not. *Suggested from your profile* above the form runs ready searches built from your target roles, seniority and strongest languages. *Location* (prefilled from the profile) keeps jobs in, or remote and open to, a city, country or region, and *Hide jobs that break my must-haves* drops the ones in the wrong place, of an engagement type you ruled out, or paying below your floor; saved searches keep both. Each row shows its tags, derived skills, level, engagement type, region and visa stance included, and the tag bar above the table narrows the rows to those carrying every tag you pick.

== Inbox

image::inbox.png[Inbox: replies grouped by day, each tagged with its kind and the job it belongs to,1200]

Replies from companies, matched to your applications and grouped by day. Each one carries its kind (interview, offer, request, rejected, acknowledgement), the job it belongs to and where it came from; the chips on top filter by kind. *Open in Gmail*, *Reply in Gmail* and *All mail for this job* link to the thread.

*Sync now* reads new mail the way Connections says: through your own Google client, an IMAP mailbox, or the AI assistant's mail connector. With the assistant, the page is covered by a *Syncing your mail* window with a progress bar, the step it is on (searching, reading, matching, logging the replies) and the time it has taken; *Cancel* stops it and keeps what was already logged. A reply that names an interview time becomes an interview on that job, with its length; an offer or a rejection proposes the stage change. Mail you sent yourself is skipped.

== Stories

image::stories.png[The story bank: three stories with their metrics, themes and the jobs each one answers,1200]

Your interview stories, one STAR story per file in `stories/` in the data folder, with front matter for `title`, `themes` and `metrics`. Each one lists the open jobs whose must-have requirements it answers, matched on the words of the requirement against the story's themes, title and facts; below the list, how many must-haves have no story yet. The `interview-prep` skill and the `behavioral-story-extractor` agent write new stories for you.

On a job, the *Interviews* tab has *Stories for this job*: every must-have with the best story for it, or a flag when there is none. The prep pack uses the same map.

== Reviews

The weekly reviews the `weekly-review` skill writes, and *What works*: from every job you applied to, how many got an answer, an interview and an offer, grouped by source, by fit band (75+, 50–74, under 50, unscored) and by month applied. A line on top names the source that answers most once it has three applications. `GET /api/funnel` returns the same numbers.

== Automation

*Preferences* has an *Automation* panel with the chores ScoutJobs does every hour while `scoutjobs serve` runs, or when you run `scoutjobs daily` from cron, launchd or n8n. Running it twice does nothing the second time. It never sends an e-mail or an application.

Daily searches:: A saved search with *Run daily* on (press it on the chip under *Find jobs*) runs once a day and adds up to 20 new matches with a score of 45 or more and no broken must-have, as `new` jobs with the posting saved.
Draft follow-ups:: When an application goes quiet past its follow-up date, or an interview is over, ScoutJobs writes the follow-up or thank-you e-mail from its template, for you to review on the job's *Emails* tab. No AI tokens.
Interview prep packs:: With an AI assistant connected, each interview in the coming week without a pack gets one queued: research on the company, the stories to tell and a prep sheet. *Build prep pack* on an interview does the same by hand.

== Connections

image::connections.png[Connections: AI assistant, mail, calendar and job sources,1200]

One card per tool ScoutJobs uses, each with *Test connection*:

AI assistant:: Claude (recommended), Codex, or a custom command from `config.yaml` (`agent_command`). It writes the tailored documents and runs the mail and calendar syncs.
Mail:: A Google account through your own OAuth client (no AI reads your mail), any IMAP mailbox (read only), or the AI assistant's mail connector. *Disconnect* forgets the choice.
Calendar:: Google Calendar, the AI assistant's calendar connector, or an Apple Calendar subscription link (read only). With the connector, *Sync now* opens a *Syncing your calendar* window like the Inbox's and syncs interviews both ways; *Sync the next* sets how many days ahead it looks (shorter is quicker).
Job sources:: The job boards *Find jobs* searches, each with an on/off switch, and the career page systems it can read.

| The next interview with its prep checklist and *Build prep pack*, past interviews waiting for an outcome, and later ones.

| Stories

| Reviews
| The files `weekly-review` writes to `reviews/<YYYY-WW>.md`, newest first, next to the funnel as it stands now, applied this week against target, follow-ups due and stale count, and *What works* by source, fit and month.

| Activity
| Every event: job added, status change, note, decision, CV check, e-mail draft or sent, file written through the API.

== JSON API

The same server answers `/api/*` with JSON, for n8n, cron and agents that cannot run the CLI. Set `api_token` and the API requires `Authorization: Bearer <token>`; the pages stay open. See xref:api.adoc[].
